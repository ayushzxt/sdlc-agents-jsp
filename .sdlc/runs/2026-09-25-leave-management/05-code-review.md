## Blocker
- `backend/src/main/java/com/example/leavemanagement/service/impl/LeaveRequestServiceImpl.java:49` and `backend/src/main/java/com/example/leavemanagement/entity/LeaveRequest.java:33` — New `Attachment` instances are attached to a `LeaveRequest` and then saved via `requests.save(...)`, but `LeaveRequest.attachment` is a `@OneToOne` without cascade and there is no explicit attachment persistence step. In practice, the create/update path can fail at flush time with a transient object or unsaved dependency error, so multipart leave creation is broken. Suggested fix: persist the `Attachment` first (or configure cascade on the association) and add a JPA-backed multipart test that covers save + update.
- `backend/src/main/java/com/example/leavemanagement/service/impl/LeaveRequestServiceImpl.java:93` and `backend/src/main/java/com/example/leavemanagement/entity/LeaveRequest.java:40` — Decision updates are performed with an in-memory status check followed by a separate `update` and then a second reload. That is still vulnerable to a race: the losing decision can hit a flush-time optimistic lock error and return a 500 instead of the required 409 conflict. Suggested fix: make the state transition atomic in the repository (already partially present via `decideIfPending`), keep the update query as the source of truth, and map optimistic-lock exceptions to the contract’s `CONFLICT` response; add a concurrent-decision test asserting the winner remains unchanged.
- `backend/src/main/java/com/example/leavemanagement/controller/AuthController.java:35` and `backend/src/main/java/com/example/leavemanagement/security/SecurityConfig.java:39` — The login contract promises rate limiting and a 429 API response, but the current app only exposes a `LoginRateLimiter` bean with no request-level enforcement beyond the controller and no explicit 429 contract test. The result is a security gap in the password endpoint and undermines the design’s login-throttle requirement. Suggested fix: enforce the limiter before authentication and add a clear 429-to-`ApiError` mapping with a red/green test covering the threshold, reset, and illegal repeated attempts.

## Should fix
- `backend/src/main/java/com/example/leavemanagement/service/impl/LeaveRequestServiceImpl.java:61` — The approver list path validates date ranges after loading the entire assigned set and then filters in memory, even though the repository already exposes start/end range queries. This creates unnecessary work and makes the list endpoint scale poorly as historical assigned requests grow. Suggested fix: push the `startDate`/`endDate` range filtering into the repository query and validate one-sided ranges explicitly before calling it.
- `backend/src/main/java/com/example/leavemanagement/security/SecurityConfig.java:43` and `backend/src/main/java/com/example/leavemanagement/controller/AuthController.java:31` — The custom login flow bypasses the normal Spring Security login mechanism and persists the security context directly; without a verified session-fixation rotation, a reused session could remain valid after successful auth. Suggested fix: rotate the session before saving the authenticated context and add an integration test that proves the pre-login session cannot continue after login.
- `backend/src/test/java/com/example/leavemanagement/controller/ApprovalControllerTest.java:20` — The approval tests are not validating the real security filter chain, so they don’t prove the API contract for unauthorized requests, CSRF, stale decision states, or multipart validation. Suggested fix: enable the security filter chain in MockMvc tests and assert 401/403/409/400 contract responses for the actual endpoint behavior.
- Browser behavior remains under-tested: loading/empty/error/success states, focus management, route guard redirects, attachment validation, and stale/forbidden decision feedback. Suggested fix: add the planned Playwright Java/browser setup and cover those flows; current Maven test execution does not validate the SPA acceptance criteria.
